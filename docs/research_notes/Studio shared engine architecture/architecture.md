# Shared runtime architecture, primary-source patterns, and enforcement

## 1. What is shared today, and what should the boundaries become?

### Takeaway

**Existing:** shared engine hosting, assets, rendering primitives and some Studio entrypoints do not establish shared end-to-end behavior. **Proposed:** three layers—generic engine, reusable Freefall runtime, Studio editor—connected by a small typed scene and viewport API. No wholesale ECS conversion is required.

### Inferences

**Proposed dependency direction:** game host and Studio editor → reusable Freefall runtime → generic engine plus existing domain crates. Generic engine must not depend on Studio, `App`, registry keys, ship-design validation or Freefall flight rules. Shared runtime must not depend on editor UI or the full game host. Split modules first if useful, then crate boundaries to enforce this; moving files alone is not consolidation.

| Layer | Minimal proposed API and ownership | Existing seams / replacements |
|---|---|---|
| Generic engine | `SceneId`, `ObjectId`, retained mesh/material handles, transforms/bounds; `ViewSpec { scene, camera, rect, target, environment, features, overlays }`; `render_views`, `ray(view,pixel)`, `pick(view,pixel,filter)`. Scene-tested and always-on-top overlays are explicit. Share renderer/cache across views. | Replace single-camera assumptions in `Game`/`Frame` and CPU projection producers; retain existing GPU cache and actual 2D UI canvas. | Reusable game runtime | `compile_design(document, registry, revision) -> PreparedCraft`; stable authored-object IDs mapped to visual/collision/interaction handles; `CraftRuntime::tick(dt, commands, environment)` and `extract_scene`; environment provider supplies sandbox or live gravity/contact/world services. | Extract consumers from `Interior`, `test_drive`, scene/mounted assembly. `App` supplies live snapshots/services; standalone supplies local records. Domain compilation never moves into generic renderer. Sources: interior.rs:6581, lib.rs:154; detailed compiler/simulation behavior belongs to specialist notes. |
| Studio editor | `EditorSession { document, selection, undo, tools, views }`; edits produce commands/revisions; UI adapters select mode presets, issue runtime commands and display runtime results. | `StudioOnly` becomes host adapter; embedded shipyard mounts the same session. Retain authoring UI, eliminate alternative physics/material/projection implementations. Sources: studio_only.rs:68, shipyard.rs:233, interior.rs:7748. |

Typed records and stable IDs are sufficient for the small scene; ECS can be evaluated later only against a demonstrated scheduling/query need. A compiler result must carry consistent transforms, COM conventions, stable IDs and revision identity through visuals, collision and picking. A delayed preparation result from revision N must not overwrite N+1. Retain the previous ready preview or explicit placeholder while preparing, and block physics activation until its prerequisites are valid. These are proposed contracts, not a claim that current code satisfies them.

Universal policy must describe behavior, not application identity: environment lights/reflections, view projection, simulation ticking, layer visibility, collision participation, audio listener, input focus/capture, and feature availability. Replace `frame.studio` with a generic environment description; the soft-box preset can be used by any client. Replace shipyard-specific resource scheduling (`lib.rs:1405`) with explicit host scheduling policy where warranted. Optional physics, world streaming, audio and diagnostics stay explicit. A text-only CODE/report view can share compilation/runtime without activating a 3D render pass.

### Gaps

Exact new type names, crate granularity, ownership across render thread and GPU-picking latency remain design choices. Full compiler behavior is outside this cross-cutting audit. Coordinator reports stable author IDs currently stop before visual/collision runtime and rotated visuals can disagree with AABB collision/picking; treat these as parity blockers to reconcile with specialist evidence, not solved by introducing an ID type. Sandbox physics must preserve richer Studio fan/battery/spring-gear experiments rather than simply substitute the current live tick; specialist simulation review owns exact extraction targets.

## 2. Which authoritative architecture patterns are applicable?

### Takeaway

Official UE, Unity and Godot interfaces support a small scene plus an editor viewport/controller using common engine services. They also demonstrate that shared renderer access does not mean every runtime feature is enabled, identical environments, or identical behavior without integration policy.

### Cited Findings

- **UE5:** `FPreviewScene` is in Runtime/Engine, owns components/lights, exposes scene/world, and supports component add/remove. `FEditorViewportClient` is in Editor/UnrealEd, receives a preview scene, owns camera/debug/editor concerns and exposes show flags. This supports separating runtime scene ownership from editor control rather than making a giant game application mandatory. — [FPreviewScene](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FPreviewScene), [FEditorViewportClient](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Editor/UnrealEd/FEditorViewportClient).
- **Retained rendering:** Epic documents scene proxies producing mesh batches, then pass processors producing draw commands; static batches are cached while dynamic batches are rebuilt. Pass selection and bindings belong to the renderer. This supports retaining resources and submitting changed instances rather than projecting every asset triangle in editor code. It does not require copying UE internals. — [Mesh Drawing Pipeline](https://dev.epicgames.com/documentation/en-us/unreal-engine/mesh-drawing-pipeline-in-unreal-engine).
- **Unity:** preview scenes isolate rendering of their contained objects. Official reference code creates a preview scene/camera, moves objects into it, and renders through camera/Graphics services. Critically, `Render(bool allowScriptableRenderPipeline = false, ...)` makes pipeline participation explicit; its mesh helpers disable shadows/probes. Shared services therefore do not prove full gameplay rendering parity. Source inspected on moving `master`, not a pinned Unity release. — [NewPreviewScene](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/SceneManagement.EditorSceneManager.NewPreviewScene.html), [PreviewRenderUtility.cs, lines 23–37, 472–487, 510–552](https://raw.githubusercontent.com/Unity-Technologies/UnityCsReference/master/Editor/Mono/Inspector/PreviewRenderUtility.cs).
- **Godot:** `SubViewport` is a view without a window, displayed through a container or texture; update policies can be once/visible/always, and standalone input is not forwarded automatically. `Viewport.own_world_3d` allows isolated world state. `EditorPlugin` inserts editor controls. These establish explicit presentation, input routing and scene isolation as separate responsibilities. — [SubViewport](https://docs.godotengine.org/en/stable/classes/class_subviewport.html), [Viewport](https://docs.godotengine.org/en/stable/classes/class_viewport.html#class-viewport-property-own-world-3d), [EditorPlugin](https://docs.godotengine.org/en/stable/classes/class_editorplugin.html#class-editorplugin-method-add-control-to-container).

### Inferences

Adopt the boundary pattern, not any engine's implementation scale: a preview scene uses the same asset/material/visibility/runtime services as gameplay, while an editor viewport owns navigation, selection and presentation. A persistent GPU resource cache plus per-frame instance submission is sufficient as the first retained path; command caching can follow measured need. No evidence collected justifies Nanite-style virtualized geometry or a wholesale ECS rewrite.

“Automatically inherits changes” should mean **compatible releases execute the same shared implementations under declared policies**, with parity CI protecting behavior. It does not mean a disabled feature activates automatically, a released binary updates itself, a changed content schema migrates without work, or an engine enhancement bypassing an old representation somehow reaches that representation. GPU capabilities and optional features need supported/disabled/unavailable states with reasons. Environment differences should be data, not hidden Studio branches.

### Gaps

Official documentation was read as architecture evidence, not a performance comparison. Epic pages currently resolve to 5.8 documentation; Godot stable and Unity master can move. No source supports a quantitative speedup for this codebase or guarantees feature equality between a preview and gameplay.

## 3. What migration and enforcement make consolidation complete?

### Takeaway

Use incremental replacement with mandatory deletion gates, not an indefinite compatibility fork. Fix the known redundant CPU work separately from the structural migration; completion requires all modes and hosts to consume the promoted common runtime, including richer Studio behavior.

**Why strangler migration:** existing shell, leases, shared input seam and GPU caches can be retained while each producer is redirected. A rewrite could provide a clean API but expands the simultaneous regression surface: save/undo, physics/resource behavior, async readiness, placement, transparency, camera controls and diagnostics. Implement vertical slices, e.g. one prepared craft in live and preview views, then WALK, DESIGN, BALANCE/DRIVE, catalogue/layout, all host routes. Temporary adapters must have named owners and removal gates; do not let two pipelines remain as permanent mode preferences. Exact conversion order can follow compiler dependencies, but material parity and responsiveness gates precede default cutover.

**Measurable completion definition:**

1. Enumerate 100% of current modes and entrypoints in a checked manifest: DESIGN incl. flat views, WALK, BALANCE, DRIVE, catalogue, Layout, CODE and report/fit/compare; standalone binary, `freefall --studio`, embedded shipyard. CODE/CLI consume shared compiler/runtime services without requiring GPU activation. Observer hull preview is a separate client, and must share relevant renderer/runtime services. Planet Studio must be explicitly classified by the owner rather than silently included or excluded by its name.
2. Every applicable manifest row names the same canonical compiler/runtime/scene extraction/rendering modules. Per-mode environment/presentation is data and optional features are explicit. There are zero alternative Studio implementations of promoted geometry/material, movement/resource/contact or interaction policy. Count module ownership and old callsites, not vague percentage code reuse.
3. A common fixture suite exercises both hosts and gameplay adapters with matched environment/time/input. Compare prepared object IDs/transforms, collision/interaction results, resource trajectories and scene packets. Compare images under matched presentation with declared tolerances; deliberate blueprint or lighting differences are profile assertions. Include rotated installations, COM, glass/masks, overlay depth, picking, readiness transitions and multi-view isolation. Every intentional difference must be traceable to documented policy.
4. CI enforces dependency direction (including build/dev edges deliberately reviewed), prohibits Studio/App imports in generic runtime, checks that editor has no GPU pipeline/shader or duplicate projector/tick ownership, and fails on unregistered modes. Prefer crate/API boundaries and compiler checks; path/symbol checks are supplemental, not proof of semantic parity. Build/test both binaries with default and no-default features in future CI; none were run during research.
5. Remove old CPU rendering producers, alternative runtime branches, migration flags and duplicate readiness/diagnostics lifecycles after their gates pass. Maintain a deletion ledger of file/symbol/remaining consumers. A retained alternate production path means consolidation is unfinished, even if unused in the default screenshot.
6. Each release ships compatible shared modules/content contracts and runs parity scenarios. Engine changes in an enabled shared feature propagate without Studio reimplementation; new optional features still require explicit policy and compatibility decisions.

**Proposed performance acceptance, not measured:** establish a fixed hardware/backend/resolution/fixture suite and record cold/warm results, p50/p95/p99 CPU per stage, GPU per view/pass, event response, first shell submission and first presentation separately, physics-ready time, upload bytes and resident/peak memory. Suggested initial target is 60 Hz (16.67 ms frame interval), with p95 event-to-visible-response under 100 ms during preparation; negotiate hardware and fixture sizes before enforcing numbers. Reject >10% reproducible regression against the newly recorded per-fixture baseline pending explanation. These are planning thresholds, not observed capability. Structural checks can be immediate: unchanged static assets cause zero CPU triangle projection and no redundant mesh reupload after residency; optional visual arrival causes zero physics rebuild unless collision input revision changes. Do not sum nested CPU scopes or parallel CPU/GPU durations. First characterize multi-view shared work so cache/upload time is not charged once to every view.

### Gaps

No throughput, memory, startup or interaction benchmark was run. Exact user 30 FPS case remains unreproduced. Transparency algorithm, offscreen-target versus atlas strategy, GPU picking latency, flat-view semantics, full articulation, required viewport count and supported device budgets remain unresolved. Compiler and simulation extraction details should use the completed specialist notes rather than be inferred from helper reuse. This proposal requires stronger semantics than either a shared projector or shared Walker/flight-control helper, but does not assert those semantics already exist.
