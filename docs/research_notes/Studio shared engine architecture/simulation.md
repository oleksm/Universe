### Inferences

- **Proposed P0:** extract one `VehicleSession::tick(command, dt, environment)` governing ordering of effective limits → control allocation → resource-constrained realized forces/torques → rigid integration/contact resolution → resource/mass/thermal state → events. Exact discretization/order must be chosen explicitly with a conservation contract; this is not a claim that the listed sequence already exists or that an integrator should be changed blindly.
- **Proposed P0:** migrate the live caller and Studio caller to that tick. Keep galaxy navigation, ATC, market, warp scheduling and cross-system handover outside it. Environment supplies gravity/up, air density/velocity/temperature, light, colliders, surface motion and contact policy; sandbox supplies a flat practice field, live supplies nearby world data. Do not make the session accept `Universe`.
- **Proposed:** make construction produce the same runtime vehicle definition and mass model from either a commissioned ship or an authoring graph. Incomplete designs get explicit capability/validation results. Distinguish authoring permissiveness from bypassing physics: “no flight computer” remains manual-only; missing power/fuel remains a physical limitation.
- **Proposed:** port fan/battery and per-leg experimental physics to domain modules before deleting Studio's simulator. If legacy landing lock and spring contact are both needed during transition, name the policies and let both hosts select them; claims of full parity require matching policies. Do not hide app-specific branches inside a nominally shared function.

**Proposed migration/deletion sequence (implementation guide, not implemented):**

1. **Define the runtime contract and canonical vehicle artifact.** Domain `VehicleDefinition`/instance state with stable actuator IDs, explicit capability results, mass distribution, resources, collision and interaction handles. Validate positive mass/inertia and incomplete designs at this boundary. 2. **Extract the live vehicle tick from `world::step_ship_at` / `flight_step` / `Devices`, then incorporate experimental devices.** Expose `EnvironmentSample`/contact queries and a `LocalWorld` scene containing one craft, ground/pad/beacon and optional obstacles. Live world performs its orchestration around that tick; Studio drives the same tick. Keep world travel/ATC outside. Migrate fans, batteries, gear models and resource realization into world/domain modules with explicitly chosen numerical behavior. This is the critical parity work.
3. **Unify construction and collision assembly.** Replace `interior::craft`'s private dynamic-body conversion and `stand_up`'s private runtime mesh/ramp assumptions with canonical compiled instances. Preserve editor-only labels/members/click-to-spawn. Compilation can support proxy fixtures explicitly; domain state should never contain rendered `equipment_visual::Placed` arrays as its definition of physical behavior.
4. **Extract WalkSession and presentation.** Replace `stand_input` with shared walk commands/session; reuse original climb volumes and interaction state. Replace duplicated Drive/Stand camera calculations with shared camera presets. Generalize HUD input from `App` to telemetry/contact/interaction views; retain Scope primitive and implement scenario markers separately from sensor sweeps.
5. **Delete once both hosts are migrated:** `Drive` physics/resource fields and `mix`/`step`/private `density`; `Craft` duplicate physics representation and `thrusters`/`body` adapters; repeated `requested_force` authority policy; Stand's private movement/input/climb policy; separate camera and flight-status computations. Keep Balance and test-drive UI as thin session clients. No migration is complete while live and Studio still call different integrators behind a shared controller API.

**Proposed scheduling/ownership contract:** one deterministic runtime tick for live and sandbox at a selected cadence, with substeps selected by the shared physics policy. Render frame accumulation and live warp/budget are host responsibilities, but total tick time, shortfall and contact events are returned explicitly. Consume key edges once and convert accumulated look deltas once; replay normalized commands at tick indices. Thermal batching must preserve accumulated owed time identically. Pause/reset/air changes are explicit scenario commands, not hidden mutation inside input sampling. “Automatic engine updates” means both hosts call the same compiled runtime implementation with matching capability policies; it does not mean a running Studio binary hot-updates when source changes.

**Proposed high-value validations: at most five contract groups, folded into the owner's existing small suite; no large mirrored test inventory.**

1. **Vehicle adapter equivalence + finite-resource impulse:** compile one asymmetric vehicle through each adapter; feed identical scripted commands/environment/tick schedule and compare normalized state, realized jets/impulse, COM/inertia and events. Include rotated body, assisted→manual and last-fuel boundary. Assert fuel/energy cannot authorize impossible impulse; compare actual session outputs, not two calls to the same helper as the entire oracle.
2. **Environment/resource/contact transaction:** small deterministic scenario phases for fan air cutoff, depleted/hot battery, plant supply and gentle/hard landing. Assert identical state transitions across hosts and conservation/finite-state invariants; named shared contact policy controls expected landing behavior. This replaces divergence, not a benchmark.
3. **Walk compiled-scene contract:** fixed route through doorway/ramp/stair/ladder and a blocked path, using one scene artifact. Compare feet/velocity, climb decision and interaction reach through sandbox/live adapters, including a frame transform on landing/takeoff. Do not assume rendering equality proves collision equality.
4. **Input/lifecycle contract:** focused vehicle, modal editor, walk and focus-loss sequence. Exactly one session receives each edge; no latent manual jet or replayed mouse delta after switch/reset; Escape/capture semantics explicit. 5. **Telemetry/target coherence:** a known pad/contact fixture checks that touchdown metrics, HUD bearing, scanner marker and camera reference derive from the same transform (catches current Z-sign mismatch). Include actual fitted sensor range versus synthetic marker classification. Use a limited visual acceptance pass for camera/HUD placement rather than numeric mirrors of drawing code.

Retain/reshape existing rotated-controller and fuel-exhaustion tests as applicable rather than expanding parallel Studio and live suites. Use deterministic fixture state, commands and ticks; no invented timing thresholds, no hardware performance assertions. Scenarios are proposed, not run.
