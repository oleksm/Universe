## 1. What is actually shared, and where do authoring, preview and commissioned behavior diverge?

### Takeaway

The strongest gap is the absence of a common full-fidelity **document → compiled ship → runtime instance** path. Sharing a parser, equipment asset cache, walk solver or flight controller does not make Studio's locally assembled test craft and collision scene equivalent to the commissioned game ship. The current entrypoint is already small; most consolidation must happen below it.

### Inferences

- **P0:** introduce a shared compiler and instantiator before deleting Studio behavior. Moving `Interior` to another crate without eliminating its alternative physics/collision construction does not meet the goal. Current divergence is supported by the separate compiler, Craft and WALK paths above.
- **P0:** isolate preview instances from live player state; class/hull identity must not serve as an instance identity. Two commissioned ships of the same hull need separate layout/state, and sandbox reset must not change a live ship.
- **P0:** implement one placement/attachment transform contract covering authored origin, envelope, equipment primary mount, hull frame and COM. Keep visual geometry, physical envelope and collision geometry distinct but identically attached; envelopes need not be mesh-exact, but their approximation must be explicit.
- **P1:** expose separate structured outcomes for `RegistryKnown`, `FitCompatible`, `AssetVerified`, `NeutralPreviewReady`, `OperationalReady`. A missing/held visual can retain an authorable object and fallback; a motion contract unsupported by the operational runtime must not silently pass commissioning.

### Gaps

- A complete authored-YAML-to-real-Ship commissioning path was not found in the audited entrypoints. The coordinator should verify any other market/refit/ship-design UI before asserting repository-wide absence; the existing functions named commission above are not that path.
- Whether preview interior modifications persist into save files or affect all simultaneously present same-class vessels was not exhaustively traced. The class-keyed storage and lack of exit rollback are confirmed; broader consequences need a dedicated runtime/save audit.
- Runtime attachment/motion implementation outside the inspected mounted consumer needs the adjacent researcher's review. No claim here that installing a package enables articulation.

## 3. How should a thin Studio own views, transactions and diagnostics while runtime/compiler services own behavior?

### Takeaway

Keep Studio's tools and workspace; move design compilation, placement, geometry, physics, scene instances, readiness and diagnostics lifecycle into shared services. Independent views must share resources and graph identity while retaining separate cameras, visibility, depth, picking and input focus.

1. **Legitimate editor ownership:** tool modes, selection sets, hover, gizmo handles, snap policy, work planes, viewport arrangement/camera navigation, source draft, transaction/undo UX, catalogue filters, layer/diagnostic visibility, save/export dialogs. Generic camera math/rays, widgets/text editing, input focus/capture and diagnostics session machinery should be reusable engine services. Editor tools invoke commands on IDs; they do not build a private physical ship.
2. **Compiler ownership:** registry resolution; all layers of geometry; typed material/equipment interpretation; fit/slot/attachment validation; mass/COM/inertia; operational collision/motion; analysis and diagnostic records; exact mappings from generated parts to authored objects. Begin by extracting tested logic, then remove duplicate algorithms only after parity; do not pretend the current Craft approximation is authoritative game physics.
3. **Runtime ownership:** instantiate the same compiled result with a context (world/environment/initial state), advance the same systems, expose queries and render instances. Static preview can pause/disable simulation by policy without a different ship builder. Catalogue preview is its own minimal scene instance using the same asset/material/attachment services and neutral capability, not a fitted operational ship.
4. **Views:** a `ViewId` owns camera/projection, viewport/scissor, render target/depth, layer visibility and pick filter; one scene can have multiple views, and one workspace can have several scenes. Preserve plan/side/end and design/inspection views, catalogue card, walk and chase. Route pointer/keyboard to focused/captured view; GUI text focus prevents flight/tool shortcuts. View projection/unprojection must be the same for drawing and gizmo/picking. Separate view depth does not imply separate asset copies; preserve shared leases. Offer real orthographic precision views while explicitly matching/migrating old long-lens behavior.
5. **Sandbox reset:** pin a compiled revision and explicit initial-state snapshot; reset runtime resources/velocities/contacts/controllers/events/environment/clock deterministically, retaining or resetting camera by an explicit UI policy. It must not write authored geometry, source draft, undo history or the live player ship. Decide explicitly whether an edit updates a paused sandbox or requires reset; show the tested revision. Asset readiness may update visuals without resetting physics or clock.
6. **Commissioning:** validate and freeze one compiled revision, then instantiate/register it in the real world with a new scene/vessel identity and persistent design provenance. Use identical object mappings/attachments/collision/actuation as sandbox. Define resource initialization, placement and world ownership explicitly; do not copy a lossy Craft back into ClassSpec, and do not derive authored identity from hull key. Sandbox state transfer, if desired, is a separate explicit operation. Never make save/export equivalent to commissioning.
7. **Change propagation:** introduce monotonic document/session revision, registry snapshot identity, asset manifest/content hashes, compiler/geometry version and instance generation. Derived tasks declare complete dependency keys, e.g. `(geometry revision, registry revision, hull content hash, deck revision, solver version, parameters)`. Publish only matching results; drop/cancel old tasks on close/reopen/reset; store per-object dirty sets for incremental transforms/structure rebuild. Asset revisions invalidate visual/material/mount-dependent output, not unrelated authoring or view state. A same-key asset edit must produce a new version identity; current native path cache cannot do that. Engine code updates propagate by common dependencies/rebuild; live code replacement is not implied or required by sharing.
8. **Diagnostics:** shared diagnostics session handles toggles, listen/record/stop, hitch scopes and close cleanup; hosts contribute scene/document/view IDs, revisions, readiness, object counts and mode-specific status. Report compilation, analysis, asset waiting, simulation, culling, projection/submission and render time distinctly. Retain capability reporting for unsupported graphics switches. Performance acceptance uses controlled future measurements, not invented targets from the prior WALK fixture.

- Run the current all-layers YAML fixture through open → visual edit → source edit → Apply → undo/redo → save/export → reopen and headless compile. Preserve every named collection, metadata field, reference, full rotation, unit, layer flag, supported source comment and unchanged scalar. Fixture exists at [`crates/core/ship-design/tests/fixtures/all-layers.ship.yaml:1`](/home/alexm/git/universe-ships-studio-architecture/crates/core/ship-design/tests/fixtures/all-layers.ship.yaml:1).
- Demonstrate stable IDs from document to render/pick/collider/actuator through asset promotion, reorder, partial recompilation, text Apply, undo/reopen and save/reload. Duplicate/copy IDs must be fresh; surviving keys must not become different selected objects; multiple same-hull instances must remain isolated.
- Compare shared compiled outputs for editor, paused preview, sandbox and commissioned ship under the same registry/asset/environment versions: object counts/mappings, local/world/COM transforms, mass/inertia, attachments, collision and climb geometry, actuator directions, material behavior and readiness. Include arbitrary roll and non-axis-aligned equipment. Do not settle for matching flight-control primitive tests.
- Verify two simultaneous editor cameras plus catalogue card and plan/side/end views with independent navigation, picking, layers, clipping/depth and text/tool focus. View changes must not mutate graph or invalidate physical compilation. Same graph edits must appear in all views without copying authoring state.
- Check pending/missing/failed/verified assets, absent mounts, stale overlays, unsupported motion, registry changes, locked and compatible dependency policies. Neither incomplete graphics nor invalid operational state should erase source objects; commissioning uses its stricter explicit readiness contract.
- Race edits against slow compile/reach/hollow/fit jobs; reopen a different design under the same visible name; change only decks, hull content, or registry facts; close/reset while work is pending. No stale revision may overwrite or be presented as the current result. Retained visuals must hold leases; closing views must release residency ownership correctly.
- Reset a changed sandbox to its pinned state, then commission the exact approved compiled revision. Verify sandbox/live ship resources and interiors remain isolated and both use the same runtime systems. Exiting a preview restores its host state without leaving anonymous hull-global design edits.
- Preserve existing source conflict detection, non-overwriting export, draft protections, atomic saves and undo grouping. Separate mutable runtime state serialization from authored document save. Remove each old path only after the replacement passes its matrix coverage.
- Re-run controlled cold/warm and multi-view performance diagnostics later with fixture, pose, GPU/renderer, concurrent processes and revision recorded. No numeric performance promise follows from this read-only audit.

### Gaps

- Compiler/runtime module names, ECS versus explicit object table, protocol transport and persistence format are design choices, not conclusions from code. A stable explicit graph can satisfy this proposal without a wholesale ECS conversion.
- Exact authored envelope semantics versus registry physical dimensions need a domain decision. Existing legacy refit mutates envelope while YAML preserves it; centralizing without deciding could silently change designs.
- Runtime resource initialization at commissioning, partially supported articulated objects, hot reload requirements, camera-reset preference and higher-fidelity YAML syntax editing need explicit product contracts. The proposed separation lets these be decided without duplicating compiler/runtime behavior.
- This audit did not execute tests or reproduce the owner's frame-rate report. All acceptance criteria remain future work.
