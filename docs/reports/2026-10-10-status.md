## What exists

The standalone `freefall-studio` and in-game studio use the same editor. New designs can have no hull, or use an existing walkable hull. The standalone launcher still imports MC-07 as a bootstrap dependency even when opening a hull-free design.

The editor implements selecting, moving, measuring, snapping, exact numeric entry, front/side/top/orbit views, undo/redo, mirror placement, grouping, copying/stamping and saved assemblies. It lays out modules, access paths with room profiles, walls/doors, frame members and decks. Engine orientation can cycle through six thrust directions. The block save schema stores centre, size and optional thrust direction; there is no general arbitrary equipment rotation/roll frame.

Registry-backed stock and equipment feed mass, power, heat, mission and lift budgets, structural load cases, member/deck sizing and pressure checks. MOUNT ALL, BRACE, AUTO-SIZE and FIT FRAME are implemented. Headless `--report`, `--compare` and `--fit` exist; `--fit` changes a design and backs it up. This audit ran only the read-only report.

Local JSON save/open and unsaved-close confirmation exist. Ordinary saves directly overwrite the plan and then the deck file: they are not an atomic transaction, and ordinary save is not the backup-producing FIT FRAME operation.

## What is verified

`equipment_visual::Placed` resolves installed equipment through one checked cache and shares geometry, colours, transforms, fallback, clipping and projection across Design, catalogue card, Walk/Preview, Balance and Test Drive. The flight renderer shares the checked asset cache, but uses a separate operational mounting/PBR path.

Current registry count:177 non-gate slotted equipment records are eligible for the catalogue;23 have visual records and154 do not. All23 referenced manifests and package file hashes passed this audit. This verifies availability, not visual acceptance of every asset in every view.

The canvas now uses per-pixel depth and perspective colour interpolation. The saved opposite-order triangle regression has zero mismatched pixels. The inspected dish image no longer shows the old rear-surface speckling. Selection/grid lines intentionally remain overlays.

The two-CH-S2 fixture verifies upright/forward models, six-axis orientation/save tests and cross-mode transforms. Its fresh report correctly shows loose engines, imbalance and missing heat rejection. It has no fuel/gear and is not a flyable acceptance craft. Its Test Drive capture crashes after ground contact: that image proves model rendering, not successful flight.

Test Drive implements rigid-body motion, placed engine torque, mass/inertia, battery discharge/heating, propellant consumption, atmosphere-dependent fans, spring legs, ground/crash reporting, assisted/manual control, mouse steering, chase camera, instruments and shared radar drawing. Four selectable atmosphere densities are available. The assisted attitude target is capped at0.698rad, approximately40 degrees—not40 percent. The cap limits the requested attitude, not all possible physical motion.

## Missing pieces and risks, in practical order

1. **One authoritative vehicle behavior path.** Rendering consolidation is real, but Test Drive still owns its controller, actuator mixing, rigid-body integration, atmosphere/drag and contact approximations. It resembles normal ship steering; it does not reuse the complete normal-flight behavior. A craft can therefore behave differently after future game integration.
2. **Geometry, selection and physics consistency.** Visible models preserve authored metres and are centred in design blocks. Resizing an envelope does not resize its mesh. Walk uses existing collision triangles and Test Drive uses block contacts/box inertia. Empty space in a detailed model can remain solid to the walker, and protrusions need not match a planning box. True mount/socket placement, arbitrary roll, detailed mesh clearance and connector routing are not supplied by this visual implementation.
3. **A complete design-to-live-ship path.** The inspected editor saves plans, generates local test craft and integrates interior layouts for existing hulls. I found no editor export/commission action that turns a new hull-free design into a normal-game ship asset/record. Existing GLB hull import is a different workflow. New outer-hull authoring, asset export and game commissioning remain a gap.
4. **Operational equipment.** Studio draws neutral meshes. An installed motion sidecar does not animate an engine, gear, ramp, clamp or hammer. The independent129-pose gear evaluator is evidence toward a future runtime consumer, not enabled landing-gear operation. MC-07 fit/clearance holds remain separate; its rework and equipment are low priority under the owner's direction.
5. **Rendering/material completion and coverage.** Base colours and camera-relative lighting work. Studio does not yet sample PBR textures/reflections; transparent-material ordering is unfinished.154 catalogue entries still fall back to envelopes. Non-engine devices lack a generic orientation/roll control in the current block representation.
6. **Acceptance and robustness.** No recorded large-design frame-time/memory benchmark was found. The shared projector still walks and projects triangles on CPU each frame. Direct Studio tests cover placement/save invariance, shared transforms/collision separation and fallback/clipping; Test Drive has a four-fan lift test. These are not full edit-save-reopen-fly-land, failure-mode, long-duration or structural qualification. Normal-save atomicity/backups also need attention.

Recommended next acceptance target: one deliberately complete small craft—engines, compatible fuel/power, legs and structure—created and saved in Studio, reopened, visually consistent in every mode, then flown and landed with measured results. Separately decide the authoritative simulation and commissioning path; adding more visible models alone will not close those gaps.
