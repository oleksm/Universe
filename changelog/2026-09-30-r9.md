# 2026-09-30 — Re-architecture R9: persistence and audit

## The world as a function of its seed and its inputs (`sim::audit`)

- **The input log.** Since R6/R7 nothing changes the world except the pilots' postings (the
  player's cockpit's included) and a few operations on it: settlers spawned, a respawn,
  trades, walking. `Universe::record_inputs` logs them tick by tick (`InputLog`): what came in
  between ticks, each tick's step, and the postings due at it.
- **Replay.** `Universe::replay` runs a world from the seed and the log alone, with no pilots;
  what they did is in the log.
- **The state hash.** `Universe::state_hash`: every ship (position, velocity, turn, state,
  hull, settings), the clock, and the services' records.
- **Saves.** A `WorldSave` is the log (its checkpoint is the seed) plus each pilot's own state,
  the cockpit's included. `world_load` replays the world, then hands the pilots back what they
  knew, so play goes on. Postings, commands and events are now serializable.

## Tools

- `UNIVERSE_RECORD=session.json cargo run --release`: the game records from its start and saves
  on exit, printing the state hash.
- `cargo run -p universe-sim --release --example replay -- session.json`: replays it and prints
  its hash.
- **Checked:** a live game session (pilots apart, the cockpit on the client side) and its
  replay gave the same hash.

## Test

`a_recorded_session_replays_to_the_same_world`: 24 settlers all leaving, plus the player's
docking autopilot, 600 ticks and about 15,000 postings. The replay reproduces the state hash,
and so does a save written to JSON and loaded (0.4 s).

## Not yet

- **Checkpoints are only at the start.** Loading a long session replays all of it; periodic
  core-state checkpoints would bound that.
- **Dev scenarios that change the world directly** (not through postings or the logged
  operations) can't be replayed.
